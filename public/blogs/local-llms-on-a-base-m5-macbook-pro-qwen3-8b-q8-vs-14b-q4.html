Local LLMs on a Base M5 MacBook Pro: Qwen3 8B Q8 vs 14B Q4

Published on Sep 13, 2026

I recently switched to a 14-inch MacBook Pro with the base Apple M5: a 10-core CPU, 10-core GPU, 16GB unified memory, and a 1TB SSD.

I wanted to use it for more than normal development. The plan is to run local models for private work, quick coding help, research reading, and experiments, while still keeping a cloud model available for difficult multi-file work.

The obvious constraint is memory. On Apple Silicon, the CPU and GPU share the same 16GB unified memory. That same memory pool also needs to leave room for macOS, an editor, a browser, and the model’s context cache. There is no separate VRAM pool that I can casually fill with a model while everything else remains untouched.

Before building a Pi-based coding harness or automating model routing, I wanted a clean answer to a basic question:

Which local model gives me the best usable quality-versus-speed tradeoff on this specific machine?

This is a baseline llama.cpp benchmark of two Qwen3 GGUF models.

The two models

I chose two models that are surprisingly close in file size:

ModelQuantizationGGUF sizeIntended role
Qwen3 8BQ8_0~8.70 GBFaster local assistant
Qwen3 14BQ4_K_M~9.00 GBBetter local reasoning/coding

The tradeoff is interesting. Qwen3 8B Q8 stores the smaller model at higher precision. Qwen3 14B Q4 stores more parameters, but each at lower precision. On a 16GB machine, both are “heavy” enough that I should run only one model at a time.

Runtime and benchmark configuration

I used llama.cpp with Metal acceleration. The important settings were:

-ngl 999      # offload all possible layers to Metal/GPU
-fa on        # Flash Attention
-ctk q8_0     # Q8 KV cache keys
-ctv q8_0     # Q8 KV cache values
-t 4          # generation CPU threads
-b 1024       # logical batch size
-ub 256       # physical micro-batch size
-r 3          # three benchmark repetitions

The benchmark used:

llama-bench \
  -hf ggml-org/Qwen3-8B-GGUF:Q8_0 \
  -hf ggml-org/Qwen3-14B-GGUF:Q4_K_M \
  -p 512 \
  -n 256 \
  -b 1024 \
  -ub 256 \
  -ctk q8_0 \
  -ctv q8_0 \
  -ngl 999 \
  -fa on \
  -t 4 \
  -r 3

The test measures two different parts of inference:

  • pp512: how quickly the model reads/processes a 512-token prompt.
  • tg256: how quickly it generates 256 new tokens.

Prompt processing matters when sending code, logs, documentation, or a large context window. Generation speed matters when the model is writing an explanation, patch, or implementation.

Results

MetricQwen3 8B Q8_0Qwen3 14B Q4_K_M
Prompt processing, 512 tokens711.54 tok/s359.71 tok/s
Text generation, 256 tokens16.13 tok/s14.44 tok/s
Model size~8.70 GB~9.00 GB
GPU offloadMetal, all layersMetal, all layers
CPU threads44
KV cacheQ8_0Q8_0

The first result is clear: the 8B Q8 model processes prompts almost twice as fast. The prompt-processing gap is much larger than the generation-speed gap, which matters most for code, logs, and other long inputs.

That matters more than I expected. If I am pasting a file, reviewing logs, or asking the model to understand an existing function, Qwen3 8B Q8 gets to generation much sooner.

The generation gap is smaller:

  • Qwen3 8B Q8: 16.13 tokens/second
  • Qwen3 14B Q4: 14.44 tokens/second

So the 14B Q4 model is only around 1.7 tokens/second slower while fitting into roughly the same model-size budget. For a deliberate coding task, that seems like a reasonable price if it produces better answers.

A real server request

I also ran Qwen3 8B Q8 through llama serve with an 8K context window and one active slot:

llama serve \
  -hf ggml-org/Qwen3-8B-GGUF:Q8_0 \
  -ngl 999 \
  -fa on \
  -c 8192 \
  -b 1024 \
  -ub 256 \
  -t 4 \
  -tb 6 \
  --parallel 1 \
  --perf \
  --host 127.0.0.1 \
  --port 8080

On a 256-token generation run, it sustained 16.25 tok/s, which is almost identical to the synthetic benchmark result.

That is useful confirmation: the benchmark is not wildly optimistic. On this M5, Qwen3 8B Q8 really does generate at around 16 tokens per second in a local server setup.

Memory and swap

The more important result was memory behaviour. During two clean single-model runs, Activity Monitor showed:

Memory metricObservation
Physical memory16 GB
Memory used~13.26–13.71 GB
Compressed memory~388.9–498.3 MB
Swap used0–256 KB
Memory pressureGreen

This looks close to the limit, because it is. But the key signal is not simply “memory used.” One clean run: green memory pressure and zero swap. macOS uses available memory aggressively for caching and compression.

What I care about is:

  • Is memory pressure green?
  • Is swap near zero?
  • Does the laptop remain responsive?
  • Does the model maintain stable generation speed?

For this run, the answer was yes. Another clean run: memory pressure remains green with only 256 KB of swap.

Earlier, I tried too many parallel slots with unnecessarily large context windows. That produced heavy swapping and made the system feel bad. The lesson was simple: 16GB is enough for one serious local model session, not for pretending I own a multi-user inference server.

Current conclusion

For daily local work, I will use both models differently:

Use caseModel
Quick explanations, logs, small files, private notesQwen3 8B Q8_0
More deliberate local coding, review, or reasoningQwen3 14B Q4_K_M
Multi-file changes, difficult debugging, long agent loopsCloud model / Codex

I am not claiming the 14B model is better yet. Throughput does not measure code quality. A model can be slower, use more memory, and still be worse at a specific coding task.

This benchmark only tells me that both models can run locally on the base M5 without active swap pressure, and that Qwen3 8B Q8 is meaningfully faster at prompt ingestion.

One unresolved part of the setup is the cloud fallback. I am still deciding between OpenRouter Go and a Codex Go subscription for difficult multi-file work and longer agent loops. The local models cover smaller and private tasks; the cloud option needs to be the reliable escalation path when the task grows.

Model routing

The end goal is not to automate everything blindly. It is to build a workflow where the model choice is visible and useful:

Route: Qwen3 14B Q4
Reason: local coding review, 3 files, estimated 6K context
Override: qwen8 | qwen14 | codex

I also want to log those decisions: task type, chosen model, latency, token usage, test result, and manual rating, so I can later see whether automatic switching actually improves the workflow.
